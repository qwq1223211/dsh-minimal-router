# 认领判据（CLAIMING）

> **默认动作是不认领。** 认领是例外，不是常态。
> 这个文件存在的目的，是把"要不要把这个标签纳入阶段管理"从感觉变成三列数。

---

## 一、两种账本，别混着算

| 账本 | 什么时候付 | 例子 |
|---|---|---|
| **工具声明**（name + description + parameters） | **每轮**都付一次（在前缀里） | 一个 `unity_*` 工具声明约 600~2000 字节 |
| **工具调用**（参数 + 结果） | **用到时**才付一次 | 一次调用几百到几千 token |

裁剪省的是第一本账。**它不该以牺牲第二本账为代价**——为了省声明字节，让模型拿不到该用的工具，
是最亏的交易（模型会改用不趁手的工具、返工、或者干脆卡住问人）。

三者成本排序大致是：**调对工具 < 手搓 < 用错工具返工 < 卡住问人**。
所以"裁掉一个会被主动调用的工具"，省的那点字节完全换不回来。

---

## 二、三条准入（必须全满足）

1. **领域专用性极强** —— 模型在别的阶段几乎不会想要它
   （例：`comfyui` 只在出图时用；`sticker` 只在发表情包时用）
2. **裁掉几乎不会误伤** —— `route_status.unclaimedTags` 里该标签 `verdict === "claim-candidate"`，
   也就是**它的工具一个都没被调用过**（`used === 0`）
3. **收益可感知** —— `bytes` 在整张工具表里占比不是几百字节那种可有可无的量

## 三、三条拒入（任一条成立就不认领）

1. 该标签的工具**有被调用过**（`verdict === "do-not-claim"`，`used > 0`）
2. **通用或跨阶段**工具（例：`ego`、`task`、`read`、`route_*`）
3. **拿不到用量数据**（`verdict === "no-data"`）——没证据就不动

---

## 四、算式（它到底值不值）

```
每轮省下   ≈ bytes × 0.25 token              （实测约 4 字节/token）
误裁代价   ≈ 一次全价重建 ≈ 当前上下文 token   （模型吃到 out-of-stage 后会自己 route_stage）
回本轮数   =  当前上下文 / (bytes × 0.25)
```

> ⚠️ **这个 0.25 只用于量级判断，不能当精确预算。**
> 它来自**英文/JSON 声明**的实测（232,458 字节 ≈ 58.3K token）；
> 如果工具描述是**中文**，token/字节会明显偏高（约 0.5–1）。
> 本插件的工具声明当前以英文为主，所以取 0.25；**换成中文描述后，实际节省会更大**——
> 但请把这里当成"数量级"，不要拿它去核对账单。

举例（本机实测数字）：

| 标签 | bytes | 每轮约省 | 43 万上下文时回本 |
|---|---|---|---|
| 一个大插件（假设 60,000） | 60,000 | ~15,000 | **约 29 轮** |
| 一个小插件（假设 3,000） | 3,000 | ~750 | 约 573 轮 |

> **结论**：短会话里认领几乎必然亏；**只有在"长会话 + 巨型工具表"时，裁剪的意义才成立**
> ——那时省的不是"一点钱"，而是"让前缀成本可控"。
> 这与 `route_status.switchEconomics`、`docs/LIMITS.md §1` 是同一套账。

## 五、怎么用（三步）

```powershell
# 1) 看清单：每个未认领标签带 bytes / used / total / verdict
route_status  →  unclaimedTags

# 2) 只对 verdict === "claim-candidate" 且尺寸可观的标签考虑认领
#    其余（do-not-claim / no-data）一律不认领

# 3) 认领写在哪：custom_stages.json（route_init 可生成模板）或 cordis.patch.yml 的 stages
```

**操作顺序（照这个顺序看，别跳）**

1. **先只看 `verdict === "claim-candidate"` 的行**，并按 `bytes` 从大到小排——收益最大的先看
2. `verdict === "do-not-claim"` 的行**直接跳过**：它有工具真的被调用过，认领就是裁掉在用的东西
3. `verdict === "no-data"` 的行**先确认 `usageTracking` 是否开启**（`route_status.toolUsage` 为 `null` 就说明关了）；
   开启但仍 `no-data`，说明该标签从未出现在用量画像里——证据不足，同样**不认领**
4. 剩下候选行，再逐个人工判断"领域专用性极强"这一条（代码判断不了）

`verdict` 三态的含义（由 `lib/stages-config.js` 的 `findUnclaimed()` 产出）：

| verdict | 含义 | 建议动作 |
|---|---|---|
| `claim-candidate` | 该标签的工具**一个都没被调用过** | 可以进一步看领域专用性再决定 |
| `do-not-claim` | 有工具真的被调用过 | **不认领**（认领就可能裁掉在用的） |
| `no-data` | 用量画像里查不到 | **不认领**（证据不足） |

> ⚠️ `claim-candidate` 是"候选"，不是"该认领"：
> **没被调用过 ≠ 不需要**——可能只是还没进过那个场景。领域专用性那一条仍然得人来判断。
>
> **证据为零 ≠ 风险为零。** 这一列只回答"有没有被用过"，不回答"以后会不会用"。

## 六、这条判据和代码的关系

| 代码 | 负责哪一部分 |
|---|---|
| `lib/usage.js` → `summarize().byTag` | 每个标签的 `used` / `total` |
| `lib/classify.js` → `tagBytesOf()` | 每个标签的 `bytes` |
| `lib/stages-config.js` → `findUnclaimed()` | 合成三列 + 给出 `verdict` |
| `lib/classify.js` → `decideOutOfStage()` | 未认领 → 永远放行（与本文档的做法互补） |

**代码只给数据，不给决定**：领域专用性无法可靠自动判断，所以这一列永远留给人。
