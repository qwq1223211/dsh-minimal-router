# A/B 对照协议（怎么跑出一对"能比"的会话）

## 第二份实测结果：allow vs deny（2026-10-31）

同一阶段（`core`）、同一任务、只差 `restrictMode`。每臂 4 个会话，从原始探针记录按 prefixSig 归并。

| 组 | tools | toolsChars | `read` 可用？ |
|---|---|---|---|
| 不裁剪（`auto`） | 172 | 138,711 | ✅ |
| **`deny`**（默认） | **72** | **50,101** | ✅ |
| **`allow`**（激进） | **39** | **17,015** | ❌ **4/4 全丢** |

### 结论：**allow 更省，但会把工具藏坏，所以默认必须保持 deny**

`allow` 的语义是"只留我点名的"。问题是**有些工具我们点不出名字**——
`read` / `write` 这类**作用域本地注册**的工具不在 `restrictableNames` 里，
我们的 allow 列表里没有它们，于是被一起藏掉。4 个 allow 会话**全部**报
`Error: unknown tool "read"`，只能改用终端读文件。

省下的字节是真的（17,015 vs 50,101，**再省 66%**），但代价是**功能缺失**。
所以：

- **`deny` 保持默认**（它只摘我们点得出名字的工具，不会误伤）
- `allow` 保留为**可选**，文档里必须写明"会隐藏点不出名字的工具，可能丢功能"

### 顺带一个漂亮的巧合

`estimatedAdvertised` 报的 **38**，在两个模式下都一样。但：

- `allow` 实际是 **39**（38 + 1 个 `run_code`）——**估算描述的其实是 allow 语义**
- `deny` 实际是 **72** —— 因为 deny 作用在更大的共享全局表（172）上

也就是说这个"估算值"一直是按 allow 的口径算的，拿它去解释 deny 的实际结果当然对不上。

## 第一份实测结果（2026-10-31，3 轮）

用 6 个子会话跑了 3 轮（每轮 A/B 各一个），任务完全相同，唯一差异是 `route_stage("core")` vs `route_stage("auto")`。
归属不是看子会话自报，而是从**原始探针记录**里按 `tools < 100`（裁剪臂）和 `messages <= 200`（子会话，排除主会话）
分桶：

| 组 | 请求数 | 平均工具数 | 平均工具字节 |
|---|---|---|---|
| **A 臂（core，裁剪开）** | 23 | 72 | **50,101** |
| **B 臂（auto，裁剪关）** | 26 | 172 | 138,711 |

> **工具声明减少 63.9%（172 → 72 个，138,711 → 50,101 字节）。**
>
> 这一项是**确定性**的：只由工具表决定，与模型说了什么无关。所以可以引用。
> 命中率两臂都 >95%，**不作为省钱证据**（子会话刚起时必然低，会拉低均值）。

### 这轮顺带抓到的三个坑（都已修）

1. **`route_status` 报的"还剩多少"是错的**：减法估 `138−100=38`、`scopedTools.schemas()` 报 `138`，
   而请求里实际是 `172−100=72`。**两个"看起来更准"的数都是错的**，所以字段已删除，
   只保留 `estimatedAdvertised`（名字里带 estimate）+ 指向探针。
2. **`scope:"session"` 分不清父会话和子会话**：有的子会话拿到的是父会话的指纹。
   现在 session 作用域额外返回 `byPrefix`（按前缀指纹分组），A/B 靠它区分。
3. **`tools === 0` 是空记录**（请求建立前），算平均值时必须排除，否则会把数字拉低 20% 以上。

> 目标：把"我觉着省"变成"两个会话实测差这么多"。
> **先说清一件事**：这个协议能给的不是"省了 X% 的账单"，而是**工具声明字节的确定性差异** + 命中率差异。
> 总 token 的差异里混着"对话本身有多长"，那不可比。

## 0. 先把变量钉死

| 变量 | 必须怎么做 |
|---|---|
| 模型 | 两个会话**同一个** provider + model |
| 插件版本 | 两个会话**同一次**加载（别中途重载，那会额外产生一次全价重建） |
| 会话 | **各开一个新的**，两边都不要接着旧会话聊 |
| 提问序列 | **逐字相同**的一组问题（见下面的样例） |
| 唯一差异 | **A 臂**：`enforceByRestrict: true` + 指定一个会砍工具的阶段<br>**B 臂**：`enforceByRestrict: false`（或停在 `auto` 阶段） |

> 想更严谨：两臂各跑 3 次，取中位数。**只跑 1 次只能算轶事**——这一点别在报告里含糊。

## 1. 跑 A 臂（装 / 裁剪开启）

1. 确认配置：`enforceByRestrict: true`，并用 `route_stage({"stage":"<会砍工具的阶段>"})` 定住。
2. 逐条发这组问题（照抄，别改字）：

```
1. 用一句话说明你在做什么。
2. 列出当前阶段你能用哪些工具。
3. 讲一个 20 字以内的冷笑话。
4. 把上一句翻译成英文。
5. 解释一下"前缀缓存"是什么。
6. 给三个你推荐的技术博客方向。
7. 用表格对比 REST 和 GraphQL 的两条差异。
8. 写一行能跑通的 hello world（任意语言）。
9. 总结上面这轮对话你记住了什么。
10. 用一句话结束。
```

3. 跑完对 AI 说：

```
调 cache_probe_report({"scope": "session"})
```

4. **记下返回里的 `session` 字段**（8 位指纹）。

## 2. 跑 B 臂（不裁剪）

1. 关掉裁剪：`enforceByRestrict: false`（或 `route_stage({"stage":"auto"})`）。
   ⚠️ **改配置要重载插件，而重载本身会产生一次全价重建**——所以：
   先重载、等一次请求跑完（那一轮会贵），**再开始数**。
2. 发**同样的 10 条问题**。
3. 同样调 `cache_probe_report({"scope": "session"})`，记下指纹。

## 3. 对比

```bash
node scripts/analysis/ab-compare.mjs --session <A的指纹> --session <B的指纹>
```

输出会给出三组数，**按可信度从高到低**：

| 指标 | 可信度 | 为什么 |
|---|---|---|
| **工具声明字节** | ✅ 最干净 | 只由工具表决定，和模型说了什么完全无关 |
| **命中率** | ✅ 较干净 | 差距大就说明某一侧缓存被打断过 |
| **promptTokens 合计** | ⚠️ 不可比 | 混着对话长度；除非两边问的字面量完全一致 |

## 4. 报告怎么写才不是自欺

❌ 不要写：

> 装了以后省了 46%

✅ 要写：

> 两臂各跑 10 轮、同一模型、同一组问题：
> **工具声明从 X 字节降到 Y 字节（−Z%）**；
> A 臂命中率 a%、B 臂 b%。
> 由于 B 臂在切换配置时重载过插件，它的第一轮包含一次全价重建，已在统计中注明。

**把 confounding（干扰项）自己先说出来**，比藏起来更可信。

## 5. 已知的干扰项（写报告时列出）

1. **重载插件** = 会话里的一次全价重建（实测能到 56 万 token）
2. **模型输出长度不稳定** → 让后续轮次的 promptTokens 不可比
3. **自动切阶段**：中途关键词命中会切阶段，产生额外重建 → 建议两臂都先 `route_stage` 定住，或把 `switchConfirmations` 调大
4. **其他插件干扰**：如果有别的插件也在改工具表，结果不干净

## 6. 一句话

> **能确定性比较的只有"工具声明字节"；命中率能看出"缓存有没有被打断"；
> 总 token 只有在两臂问的字面量完全相同时才有意义。**
>
> 任何"省了 N%" 的说法，都要能回答：**N 是怎么算出来的、干扰项是什么。**
